# Chainlink

## What this skill does
Chainlink provides decentralized oracle networks delivering price feeds, verifiable randomness (VRF), and cross-chain interoperability (CCIP) to smart contracts across all major EVM chains. This skill teaches an AI agent how to read oracle data, verify feed health, and interact with Chainlink services.

## Supported chains
- All major EVM chains (Ethereum, Base, Arbitrum, Optimism, Polygon, Avalanche, BNB Chain, Fantom, Gnosis, Scroll, Linea, zkSync Era, and more)

## Common operations
### Reading Price Feeds
1. Chainlink price feeds implement the `AggregatorV3Interface`. Call `latestRoundData()` on the feed contract to get: `roundId`, `answer` (price), `startedAt`, `updatedAt`, and `answeredInRound`.
2. The `answer` field returns the price as an int256 with a fixed number of decimals. To get the human-readable price, divide by `10 ** decimals()` (typically 8 for crypto pairs, varying for forex/commodities).
3. For ETH/USD with 8 decimals, an answer of `250000000000` means $2,500.00 per ETH. Always read the `decimals` field to correctly parse the price.
4. Check feed health by comparing `updatedAt` to the current block timestamp. If the answer is older than the feed's heartbeat (typically 1 hour for crypto, 24 hours for others), the data may be stale. Also check `answeredInRound` equals `roundId` to ensure data is from the current round.
5. Chainlink reference page: `https://docs.chain.link/data-feeds/price-feeds/addresses` for the complete list of feed addresses by chain. Use the most specific pair (e.g., ETH/USD not ETH/USDT) for accurate pricing.

### Historical Price Data
1. Call `getRoundData(roundId)` to retrieve data from a specific oracle round. Each round is identified by a round ID (uint80).
2. To find a historical round near a specific timestamp, use a binary search approach: `getRoundData(latestRound)` to get the latest timestamp, then estimate which round corresponds to the target time using the average round interval.
3. Alternatively, query the feed's `phaseId` and `aggregatorRoundId` using `latestRoundData()`, then iterate backwards through rounds using `getRoundData(roundId - n)`.
4. Compute the price change over time: `(currentPrice - historicalPrice) / historicalPrice * 100` to calculate percentage change.
5. Present historical data clearly: "ETH/USD is currently $2,500.00, up 5.2% from $2,376.50 one month ago."

### Cross-Chain Verification
1. Compare the same feed across multiple chains to detect anomalies. The ETH/USD price should be nearly identical on Ethereum, Arbitrum, and Base (within 0.1-0.2% due to update timing).
2. If prices diverge significantly (>0.5%), it may indicate an oracle issue on one chain or an arbitrage opportunity. Warn the user about potential risk.
3. Each chain has its own set of Data Feed DONs (Decentralized Oracle Networks) with different node counts and heartbeat intervals. Ethereum mainnet feeds tend to have the most nodes and fastest updates.
4. For cross-chain operations, use CCIP (see below) to read a verified price from the source chain rather than trusting different feeds on different chains.

### Verifiable Randomness (VRF)
1. Chainlink VRF provides on-chain verifiable randomness for applications like gaming, NFTs, lottery draws, and randomized allocation.
2. To request randomness, a contract calls `requestRandomWords(keyHash, subId, requestConfirmations, callbackGasLimit, numWords)` on the VRF Coordinator contract. This is a contract-level operation, not typically done via wallet transactions.
3. The subscription manager at `vrf.chain.link` allows creating and funding VRF subscriptions with LINK tokens.
4. For agents interacting with VRF-enabled contracts, check the `fulfillRandomWords(requestId, randomWords)` callback to verify that the returned randomness was generated by Chainlink VRF.
5. Verify that the VRF request was fulfilled by checking the VRF Coordinator's event logs for `RandomWordsFulfilled(requestId, randomWords, payment)`.

### Cross-Chain Interoperability (CCIP)
1. CCIP enables secure cross-chain token transfers and arbitrary messaging. The CCIP Router contract acts as the entry point on each chain.
2. To send tokens cross-chain, encode `ccipSend(destinationChainSelector, message)` where the message includes `receiver`, `tokenAmounts`, `data`, and `feeToken`. The `destinationChainSelector` is a uint64 identifier for the target chain.
3. CCIP fees are paid in the source chain's native token (ETH on Ethereum) or in LINK. Fetch the fee estimate via the CCIP Router's `getFee(destinationChainSelector, message)` function.
4. Token transfers via CCIP use the Lock-and-Mint or Burn-and-Mint mechanism with the Token Pool contract. The token must have an active CCIP token pool on both source and destination chains.
5. Cross-chain messages can carry arbitrary calldata along with token transfers, enabling cross-chain contract calls (e.g., "transfer USDC to Arbitrum AND deposit it into Aave").
6. For simple balance checks, use the Chainlink Data Streams API (for low-latency pricing) or standard price feeds. Only use CCIP when you need to move tokens or execute cross-chain logic.
