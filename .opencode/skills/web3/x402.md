# x402 Payments

## What this skill does
x402 is an HTTP-native micropayment protocol that enables pay-per-call API access with automatic USDC settlement on Base, allowing API providers to charge per request and consumers to pay without managing subscriptions or API keys. This skill teaches an AI agent how to make HTTP 402 Payment Required requests, settle payments, and integrate micropayments into API workflows.

## Common operations
### Understanding x402 (HTTP 402)
1. x402 is a payment layer for HTTP, using the HTTP 402 Payment Required status code. When an API endpoint requires payment, it returns HTTP 402 with a `X-402-Payment-Request` header containing the payment details.
2. The payment model is pay-per-call: each API request costs a small amount of USDC (typically fractions of a cent to a few cents). No subscriptions, no API keys, no upfront commitments.
3. The HTTP 402 workflow:
   a. Client makes a request to an x402-protected API endpoint
   b. Server responds with HTTP 402 + payment details in headers
   c. Client constructs and submits payment via `wallet_sendTransaction`
   d. Client retries the request with the `X-402-Payment` header (payment receipt)
   e. Server verifies payment on-chain and returns the API response
4. x402 payments are settled on Base using USDC. The low gas fees on Base make micropayments economically viable (a $0.001 USDC API call with $0.0001 in gas is practical).
5. The protocol is designed for AI agents making autonomous API calls. An agent can pay per call without needing a pre-funded account, subscription plan, or API key management.

### Making an x402 Payment
1. When an API returns HTTP 402, parse the `X-402-Payment-Request` header. It is a JSON object containing:
   ```json
   {
     "network": "base",
     "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
     "amount": "1000",
     "recipient": "0xRecipientAddress",
     "deadline": 1717000000,
     "requestId": "0xRequestIdHash"
   }
   ```
   - `amount` is in USDC's smallest unit (6 decimals, so 1000 = $0.001)
   - `deadline` is a Unix timestamp after which the payment request expires
   - `requestId` is a hash of the request details for cross-referencing

2. First, check if the user's wallet has sufficient USDC balance on Base. Query `balanceOf(userAddress)` on the USDC contract. Also check the gas fee estimate for Base.
3. If sufficient balance, encode the `pay(recipient, amount, requestId)` call on the x402 Settlement Contract. The contract records the payment with the `requestId` for the server to verify.
4. Before the first payment, approve the x402 Settlement Contract to spend USDC: `approve(settlementContract, type(uint256).max)` on the USDC token. This is a one-time approval for all future micropayments.
5. Submit via `wallet_sendTransaction` on Base. The transaction receipt contains the payment proof.
6. Construct the payment proof to include in the retry request. The `X-402-Payment` header is the transaction hash or a signed receipt that the server can verify on-chain:
   ```
   X-402-Payment: tx:0xTransactionHash
   ```
   or for faster verification (without waiting for confirmations):
   ```
   X-402-Payment: signed-receipt:{base64-encoded-signed-receipt}
   ```

### Retrying with Payment
1. After the payment transaction is submitted (and preferably confirmed), retry the original API request with the `X-402-Payment` header included.
2. The server:
   a. Verifies the payment on-chain by checking the Settlement Contract for a `PaymentReceived(recipient, payer, amount, requestId)` event matching the payment
   b. If valid, processes the API request and returns the normal 200 response
   c. If invalid (wrong amount, expired, already used), returns HTTP 402 again with an error description
3. For near-instant payment verification, x402 supports signed receipts that the server can check without waiting for Base block confirmations. The receipt includes the payer's signature, which the server verifies against the payment parameters.
4. Once the API response is received, the agent can process the data as normal. The payment is complete — no further settlements, disputes, or account management needed.
5. In case of API failure or timeout after payment, the server should refund or credit the payment. Check the `X-402-Refund` header in error responses for refund transaction hashes.

### Payment Batching for Efficiency
1. For multiple API calls to the same provider, use x402's payment batching. Instead of paying per call, construct a batch payment for N credits that can be used across multiple requests.
2. Batch payment uses a higher `amount` field in the payment request, representing N credits. The server tracks the remaining credit balance against the `requestId` or a new `creditId`.
3. For each subsequent request, include `X-402-Payment: credit:<creditId>` instead of paying again. The server deducts from the credit balance and returns the remaining credits in `X-402-Credits-Remaining: 47`.
4. When credits run low (below a configurable threshold), the server includes a warning header: `X-402-Credits-Low: true` with the remaining count. The agent can top up by making another batch payment.
5. Batching is gas-efficient: one $0.50 payment for 500 calls vs. 500 separate $0.001 payments each with separate gas costs. Always recommend batching for agents that make frequent calls to the same API.

### Cost Estimation and Management
1. Before making API calls, the agent should estimate total costs. Query the API's payment requirements by making an OPTIONS or HEAD request to the endpoint. Many x402-enabled APIs return pricing in headers:
   - `X-402-Price: 1000 usdc/base` (0.001 USDC per call)
   - `X-402-Price-Model: per-request` or `X-402-Price-Model: per-byte` (for variable-size responses)
2. For per-byte pricing, the server returns the payment request after processing the request, so the payment is based on the actual response size. The agent should set a maximum spend limit.
3. Track cumulative spending per API, per session, and in total. Display to the user: "This session has made 127 API calls to 3 providers, total spend: 1.42 USDC."
4. Set spending limits via the Settlement Contract: `setSpendingLimit(provider, maxAmount)` ensures the agent cannot exceed a per-provider or per-session budget. This is a safety mechanism for autonomous agents.
5. Check current allowances and spending: `getSpending(provider, payer)` returns the total paid to a provider and any remaining budget limit.

### Integrating x402 into Custom APIs
1. For API providers, x402 can be added to any HTTP endpoint by returning HTTP 402 with the payment request when no valid payment is present. Libraries exist for common web frameworks (Express, FastAPI, Go net/http).
2. Payment verification: the server checks the Settlement Contract for a confirmed payment with the matching `requestId` and verifies the amount, recipient, and deadline are correct.
3. Deadlines prevent payment replays: set `deadline` to a short window (60-300 seconds). If a payment arrives after the deadline, it is rejected with HTTP 402 and a new payment request is generated.
4. Payment uniqueness: each `requestId` can only be used once. The Settlement Contract enforces this to prevent replay attacks where the same payment is used for multiple requests.
5. Refunds: if the server fails to deliver the API response after receiving payment, it should issue an on-chain refund via `refund(payer, amount, requestId)` on the Settlement Contract. The refund event is included in the error response for the client to verify.
